## 3. Аутентификация

1. **Email + пароль.** Регистрация → письмо со ссылкой подтверждения (через outbox → SMTP в mailpit). Неподтверждённый пользователь может войти, но видит баннер и не может приглашать участников или платить.
2. **Сессии.** Access JWT на 15 минут хранится в памяти фронтенда. Refresh-токен — случайная строка в **httpOnly, Secure (кроме dev), SameSite=Lax cookie** на путь `/api/auth`. В БД хранится только SHA-256 хэш.
   - **Ротация:** каждый `/auth/refresh` выдаёт новый refresh и помечает старый `revoked`, `replaced_by_id`.
   - **Обнаружение повторного использования:** если пришёл уже отозванный токен — отозвать всё семейство (`family_id`) и вернуть 401. Отдельный тест.
   - `/auth/logout` отзывает текущий, `/auth/logout-all` — все токены пользователя.
   - CSRF: refresh-cookie доступна только `POST /api/auth/refresh` и `logout`, фронт шлёт заголовок `X-Requested-With`; проверяй его.
3. **Сброс пароля:** одноразовый токен на 30 минут, хэш в БД. После сброса отзываются все refresh-токены. Ответ на запрос сброса одинаковый для существующего и несуществующего email.
4. **OAuth через GitHub** (authorization code + `state` в подписанной cookie). Включается только если в `.env` заданы `GITHUB_CLIENT_ID/SECRET`; иначе кнопка скрыта, а эндпоинт отвечает 404. Если email из GitHub совпадает с подтверждённым локальным аккаунтом — привязать; с неподтверждённым — не привязывать, показать ошибку.
5. **Rate limit** (из tutorbot): логин, регистрация, запрос сброса пароля, refresh.
6. **Демо-вход.** Кнопка «Попробовать без регистрации» на лендинге создаёт свежего `is_demo` пользователя с заполненным воркспейсом (3 участника-бота, 2 проекта, ~25 задач, активный trial Pro) и сразу логинит. Cron в воркере удаляет демо-данные старше 24 часов. Демо-пользователь не может менять email/пароль и подключать OAuth.

## 4. Воркспейсы, роли, права

- Пользователь может быть в нескольких воркспейсах. При регистрации создаётся личный воркспейс. В шапке есть переключатель воркспейсов. URL: `/w/:slug/...`.
- Роли и права — словарь `PERMISSIONS` как в repairdesk. Минимум:
  - **owner**: всё, включая биллинг, удаление воркспейса и передачу владения.
  - **admin**: участники и инвайты (кроме owner), проекты, статусы, просмотр счетов.
  - **member**: задачи и комментарии, просмотр участников.
  - **guest** (только Pro): читать и комментировать в проектах, куда добавлен. Гость не занимает платное место.
- API: `/api/w/{workspace_id}/...`. Зависимость `get_membership` достаёт членство. Не участник получает **404** (не 403), чтобы нельзя было перебором узнать, какие воркспейсы существуют. Участник без права получает **403** + запись `ACCESS_DENIED` в лог.
- **Инвайты:** ссылка с токеном на 7 дней, можно отозвать и отправить повторно. Принять может только залогиненный пользователь с тем же email. Перед созданием инвайта в Pro API возвращает предпросмотр доплаты (см. §5), фронт показывает «Будет списано X ₽ за остаток периода» и требует подтверждения.
- Удаление участника: его задачи остаются без исполнителя, место освобождается со следующего периода.

## 5. Тарифы и биллинг (главная часть проекта)

### Тарифы

| | Free | Pro |
|---|---|---|
| Цена | 0 | **490 ₽ за место в месяц** или **4 900 ₽ за место в год** |
| Участники (owner+admin+member) | до 3 | без лимита, каждый — платное место |
| Гости | нет | да, бесплатно |
| Проекты | до 3 активных | без лимита |
| Кастомные статусы колонок | нет (фиксированные: To do / In progress / Done) | да |
| История активности | 7 дней | полная |
| Экспорт задач в CSV | нет | да |

Тарифы и лимиты описаны **в одном месте** кода (`app/billing/plans.py`). Проверки лимитов — в сервисном слое, с понятными кодами ошибок (`plan_limit_members`, `plan_limit_projects` и т.п.). Фронт по этим кодам показывает модалку «Перейдите на Pro».

### Биллинг-логика — своя, провайдер только проводит платежи

Подписки, места, пропорциональные доплаты, продления и dunning считаются **в нашем коде** (`app/billing/`). Платёжный провайдер скрыт за интерфейсом и умеет только: создать платёж с redirect на оплату (с сохранением карты), списать с сохранённого метода, принять вебхук.

```python
class PaymentProvider(Protocol):
    name: str
    async def create_checkout(self, *, invoice: Invoice, return_url: str, save_method: bool) -> CheckoutSession: ...
    async def charge_saved_method(self, *, invoice: Invoice, method: PaymentMethod, idempotency_key: str) -> ChargeResult: ...
    async def parse_webhook(self, raw_body: bytes, headers: Mapping[str, str]) -> ProviderEvent: ...  # проверка подлинности внутри
```

**Провайдеры:**
1. **`mock` — обязателен и включён по умолчанию**, проект должен полностью работать без внешних ключей.
   - Собственная страница оплаты `/mock-checkout/:session` на фронте, оформленная как тестовая (баннер «Тестовый платёж»).
   - Тестовые карты: `4242 4242 4242 4242` — успех; `4000 0000 0000 0002` — отказ; `4000 0000 0000 9995` — успех при оплате, но последующие автосписания отклоняются (для демонстрации dunning).
   - После «оплаты» mock-провайдер **отправляет вебхук на наш же эндпоинт** через outbox-команду (HTTP POST с HMAC-SHA256 подписью сырого тела, как в tutorbot), а не меняет состояние напрямую. Так путь «вебхук → состояние» один для всех провайдеров.
   - Флаг `MOCK_WEBHOOK_DUPLICATE_RATE` (по умолчанию 0.2): часть вебхуков отправляется дважды — идемпотентность видна в логах и тестах.
2. **`yookassa` — адаптер**, включается `PAYMENT_PROVIDER=yookassa` + `YOOKASSA_SHOP_ID/SECRET_KEY` тестового магазина. Платёж с `save_payment_method`, автосписания по `payment_method_id`, заголовок `Idempotence-Key`. Подлинность вебхука YooKassa: подписи нет, поэтому проверять IP по официальному списку **и** перезапрашивать объект платежа через API, доверяя только ответу API. Покрыть тестами на фикстурах с замоканным HTTP. Реальный сетевой вызов в тестах не нужен.

### Сценарии, которые должны работать и быть покрыты тестами

1. **Trial.** Перейти на Pro можно с 14-дневным trial без карты. За 3 дня до конца — письмо. В конце trial: если карта есть — списание и `active`; если нет — откат на Free (с применением правил даунгрейда, см. п. 7).
2. **Апгрейд Free → Pro.** Выбор периода (месяц/год) → счёт на `seats × цена` → checkout → вебхук `payment.succeeded` → `active`, сохранён `payment_method`. Статус меняется **только по вебхуку**. Страница возврата опрашивает статус и показывает «Ожидаем подтверждение оплаты…», пока вебхук не обработан.
3. **Добавление места в середине периода.** Доплата = `цена_за_место × оставшиеся_секунды / секунды_периода`, округление до копейки `ROUND_HALF_UP` через `Decimal`. Создаётся счёт `proration`, списывается с сохранённого метода, место добавляется после успешного вебхука. Инвайт до этого — в статусе «ожидает оплаты места». Одновременные инвайты не должны дважды посчитать одно место: Redis-лок из tutorbot или `SELECT … FOR UPDATE` на подписке. Тест на конкурентность.
4. **Уменьшение мест.** Записывается в `pending_seats`, применяется при продлении. Денег не возвращаем, в UI так и написано.
5. **Продление.** Cron в воркере раз в минуту находит подписки с `current_period_end <= now` и создаёт outbox-команду `RENEW_SUBSCRIPTION`: применить `pending_seats`, создать счёт, списать с идемпотентным ключом `renewal:{workspace_id}:{period_start}`. Повторный запуск не должен создать второй счёт: UNIQUE в БД + тест.
6. **Неудачный платёж (dunning).** `past_due`, баннер у всех участников, письмо owner. Повторные списания через 1, 3 и 5 дней. Через 7 дней → `read_only`: все изменяющие эндпоинты воркспейса отвечают `402 workspace_read_only` (реализовать одной зависимостью `require_writable`), чтение работает. Owner может обновить карту и оплатить сразу, тогда сразу `active`.
7. **Отмена и даунгрейд.** Отмена → `cancel_at_period_end`, до конца периода всё работает, можно отменить отмену. В конце периода → Free. Если лимиты Free превышены: лишние проекты (кроме 3 последних изменённых) архивируются и становятся read-only, лишние участники остаются, но приглашать новых нельзя, пока их больше трёх. **Никакие данные не удаляются.**
8. **Смена периода месяц → год:** с начала следующего периода. Сделай, если укладываешься. Иначе — в «Намеренно не реализовано».

### Вебхуки — паттерн из repairdesk

`POST /api/billing/webhooks/{provider}`:
1. Проверка подлинности (провайдер-специфично). Неподлинный → 401, ничего не сохраняем.
2. Сырое тело + заголовки сохраняются в `raw_webhook_deliveries` и **коммитятся до разбора**.
3. `webhook_events` с `UNIQUE(provider, provider_event_id)`. Повтор → `200 duplicate`. Тот же id с другим содержимым → `409` + `SystemIssue`.
4. Изменение подписки и счёта — **в той же транзакции**, что вставка события. Гонку двух одновременных доставок решает ограничение БД. Тест на параллельную доставку.
5. Каждое изменение биллинга пишется в `activity_log` (`billing.*`).

**Все переходы статусов подписки — в одной функции-автомате** с явной таблицей допустимых переходов. Недопустимый переход → исключение + `SystemIssue`. Unit-тесты на таблицу.

## 6. Канбан и задачи

- Проекты: создание, переименование, архивирование. Колонки-статусы: на Pro — добавление, переименование, удаление (только пустой колонки), сортировка.
- Доска: колонки, карточки (номер `PRJ-12`, заголовок, исполнитель-аватар, приоритет, срок). Drag-and-drop между колонками и внутри колонки, оптимистичное обновление через TanStack Query с откатом при ошибке.
- Модалка задачи: заголовок, описание (простой textarea с markdown-рендером), исполнитель, приоритет, срок, комментарии, история изменений задачи из `activity_log`.
- Фильтры доски: исполнитель, приоритет, «только мои». Глобальная страница «Мои задачи» по всем проектам воркспейса.
- **Real-time:** SSE-эндпоинт `/api/w/{id}/events` (авторизация access-токеном в query-параметре с коротким TTL или через cookie — выбери и запиши в DECISIONS). Изменения публикуются в Redis pub/sub после коммита. Открытая доска у второго пользователя обновляется без перезагрузки.
- Лог активности воркспейса: страница с пагинацией по курсору. На Free — только последние 7 дней (фильтр на сервере).
- Экспорт CSV (Pro): потоковая выдача `StreamingResponse`.

## 8. Тесты и качество

**Backend (pytest, против настоящих Postgres и Redis, как в tutorbot), цель покрытия ≥ 85% по `app/billing` и `app/api`.** Обязательные тесты:
- Auth: регистрация, гонка двух регистраций, логин, rate limit, ротация refresh, **reuse detection отзывает семейство**, logout-all, сброс пароля отзывает сессии, подтверждение email, одинаковый ответ на сброс для несуществующего email.
- Тенантность: пользователь A не может прочитать, изменить или переместить задачу, проект, комментарий или участника воркспейса B (**404**); member не может то, что может admin (**403** + `ACCESS_DENIED` в логе); нельзя назначить исполнителем не-участника; нельзя переместить задачу в статус чужого проекта.
- Биллинг: расчёт proration (граничные случаи: первая и последняя секунда периода, год, округление); апгрейд по вебхуку; дубль вебхука; конфликт содержимого; параллельная доставка; параллельные инвайты не превышают места; продление идемпотентно; dunning-цепочка до `read_only` и выход из неё; отмена и возобновление; даунгрейд архивирует лишние проекты и ничего не удаляет; таблица переходов автомата.
- Outbox: ретраи с backoff, перманентная ошибка, `SKIP LOCKED` с двумя воркерами.
- Время в тестах — через инжектируемые часы (`Clock`), без `sleep`.

**Frontend:** `tsc --noEmit`, ESLint, `vite build` без ошибок. **Playwright e2e** (`frontend/e2e/`) — один сквозной сценарий против поднятого compose: регистрация → подтверждение письма через API mailpit → создание проекта и задачи → перетаскивание карточки → апгрейд на Pro через mock-checkout картой 4242 → видим статус Pro → приглашение второго участника с доплатой.

**CI (GitHub Actions):** джоб backend (взять из tutorbot), джоб frontend (lint, typecheck, build), джоб e2e (docker compose up, playwright). Бейдж CI в README.
